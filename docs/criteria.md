# Критерії успіху та блокування атак

## 1. SQL Injection (SQLI)

**Ендпоінт:** `GET /search`

- **Атака успішна:** відповідь містить записи, які не відповідають буквальному пошуку, дані `password_hash` або текст SQL-помилки.
- **Заблоковано:** сторонні записи не повертаються, SQL-помилки не розкриваються.
- **Легітимні тести:**
  - `q=alice` → рівно один запис Alice.
  - `q=a` → записи Alice та Admin (відповідно до тестових даних).

## 2. Reflected Cross-Site Scripting (XSS-R)

**Ендпоінти:** `GET /search`, `GET /greet`

- **Атака успішна:** введений payload потрапляє у відповідь в небезпечному, неекранованому HTML-контексті.
- **Заблоковано:** спеціальні символи коректно екрануються відповідно до контексту виведення.
- **Легітимний тест:** `q=5 < 6` → текст відображається без виконання HTML або JavaScript.

## 3. Stored Cross-Site Scripting (XSS-S)

**Ендпоінт:** `POST /comments`, перевірка через `GET /comments`

- **Атака успішна:** збережений payload під час перегляду коментарів інтерпретується браузером як активний HTML або JavaScript.
- **Заблоковано:** користувацький вміст екранується під час виведення.
- **Легітимний тест:** коментар `5 < 6 & 7 > 3` зберігається та відображається як звичайний текст.

## 4. Cross-Site Request Forgery (CSRF)

**Ендпоінт:** `POST /profile/email`

- **Атака успішна:** запит з іншого сайту без валідного CSRF-токена змінює email користувача.
- **Заблоковано:** сервер відхиляє запит (очікувано `403`), а email залишається незмінним.
- **Легітимний тест:** запит із валідним токеном успішний (`200`), email змінюється.

## 5. Insecure Direct Object Reference (IDOR)

**Ендпоінт:** `GET /notes/<id>`

- **Атака успішна:** користувач отримує доступ до нотатки іншого користувача (`200`), а `owner_id` не збігається з його ID.
- **Заблоковано:** сервер відхиляє доступ до чужої нотатки (`403`).
- **Легітимний тест:** користувач отримує доступ до власної нотатки (`200`).

## 6. Brute Force (BRUTE)

**Ендпоінт:** `POST /login`

- **Атака успішна:** після визначеної кількості невдалих спроб сервер не застосовує очікуваного обмеження.
- **Заблоковано:** після досягнення ліміту сервер обмежує подальші спроби (наприклад, `429 Too Many Requests`).
- **Легітимний тест:** правильні облікові дані дозволяють увійти в систему.
- **Параметри тесту:** кількість спроб і часовий інтервал будуть визначені на День 5.

---

## Примітки до методології

1. Для кожної атаки потрібно використовувати однаковий набір тестів у Flask, Django та FastAPI.
2. Успіх атаки визначається за фактичною поведінкою застосунку, а не лише за HTTP-статусом.
3. Легітимні тести потрібні для перевірки того, що захист не блокує нормальні запити.
4. Результати кожного тесту зберігаються у CSV для подальшого аналізу.
5. Усі навмисно вразливі застосунки використовуються лише в ізольованому навчальному середовищі.
